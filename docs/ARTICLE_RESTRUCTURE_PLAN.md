## 何を残し、何を削るか ―― 判断基準は「読者の ROI」

著者の指摘(2026-09-02): **「そもそも我々にとって学びでも、読者の ROI とは
一切関係ないなら書かなくてもいい気がする。」**

これは組み替えより先に効く基準である。組み替えは**残すと決めたものの並べ方**
の話でしかない。まず**削る**。

**判定**: その節を読んだ読者が「自分の仕事で使える判断・手順・数字」を
持ち帰れるか。持ち帰れないなら、こちらの内部記録(コミットメッセージ・
memory・docs)に置けば足りる。

| 残す(読者の ROI がある) | 削る/縮める(こちらの内部事情) |
|---|---|
| 「発見ゼロ」が未実行の偽装でありうる、という**誰でも自分の検査に当てはめられる**話 | 私が換算係数を渡し忘れて誤読した、という**その場の操作ミス** |
| 型を分ける判断基準(混ぜたら例外か、もっともらしく間違うか)+ 296,000 倍の実例 | 型述語を `isinstance` で書いて自分で誤検出した、という**書き間違い** |
| 位相シフト法が λ/4 で破綻する比較表(**既存手法の限界**として実務に効く) | 台帳の内部変数名や配線先ファイルの話 |
| 四元数の正直な結論(QFT は買わない / Riesz は負けた)= **読者が同じ選択で迷う** | どの Agent が何を報告したか、という**制作過程** |
| 「比較は同一 split で取る」= 誰の実験にも効く規律 | 「+38% と書きかけた」という**個人的なヒヤリハット**(規律だけ残し、当事者の失敗談は縮める) |

**具体的にこの記事へ当てるなら**: 「自分と AI の誤りを 5 件」は現状 5 件とも
等しい紙幅だが、読者 ROI があるのは (1) 同一 split で比較する (2) 基準線は
既存で最良の手を使う ―― の 2 つ。残る 3 件(述語の書き間違い、Agent の自己
訂正 2 件)は **1 段落に圧縮するか落とす**。「AI にレビューさせると自分に
有利な数字を訂正してくることがある」という一般化だけ残せば足りる。

同様に「副産物 ―― 公開直後の API のバグ」は、**教訓(ε を分母に足すと
系統的に縮む)は残し、経緯は縮める**。

**逆に増やすべきもの**: 読者が自分の環境で**再現・流用できる形**。
コマンド、閾値の決め方、何をどう測ったか。ここは削らない。

検査。PATCH 後に再 GET して反映を確認。トークンは
`~/.config/qiita-cli/credentials.json` の `credentials[].accessToken`。
