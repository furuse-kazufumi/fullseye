# GPU 穴埋め候補 10 op の採否(D') — 2026-11-02

候補は幾何変換・特徴・計測・周波数・分解系を優先し、**scikit-image/OpenCV の包み (`xsk_*` / `sk_*` / `cv_*`)は本体が CPU ライブラリなので対象外**とした。
各候補: torch 実装 → `parity()`(内部差 < 5e-3)→ loco(RTX 5090)で実寸 bench。

採否は **実寸の倍率**で決める(小画像で負けても実寸で意味のある倍率なら採用。閾値 5.0x)。parity が 5e-3 を超えた候補と、実寸でも CPU に勝てない候補は**登録しない**。

- `corner_response` — 実寸 2048^2 で 17.6x(小画像 512^2 は 22.9x)
- `anisotropic_diffusion` — 実寸 2048^2 で 144.1x(小画像 512^2 は 145.3x)

## 登録しなかった op と理由

- `abs_image` — 実寸でも 3.1x 止まり(メモリ律速、登録しない)

## 計測の作法と正直な内訳

- CPU = 登録経路そのもの(`ops.RT[op]` を画像 1 枚ずつ、float64)。前生成した同じ画像で測り、乱数生成は時間に含めない。
- GPU = **host→device 転送 + op + device→host 転送**を含む単 op のコスト(`accel.run_batch` と同じ経路)。
- 2048² x50 の GPU 時間はどの op も **約 0.5 s を下回らない = 転送床**(0.8 GB 往復)。pointwise op (`cos_image` / `companding_mu_law`)の倍率はこの床と CPU の float64 逐次処理の比であり、計算の勝ちではない。常駐パイプライン(`run_pipeline`)の中では転送が償却され、pointwise op のコストはほぼ 0 になる。
- 最初の計測は GPU 上で乱数を生成し転送を含めていなかったため、pointwise でも 600x 超が出た。異常値として内訳を疑い、転送込みに直した上の表が正本(第 1 便の threshold 0.73x と同じ向きの作法)。
- ログ: `docs/perf/logs/d_bench.log`。寸法ごとの CPU は 512² で 10 枚、2048² で 3 枚を実測し N に線形(同一寸法内の枚数方向のみ)。


## 候補の母集団(10 以上を検討、8 を計測)

- 計測した 8 op: 上の表。
- `derivate_gauss`(edges): scipy の order=1 ガウス微分核の重み計算を torch で逐語再現する必要があり、この便では parity 未確認のため計測しなかった(次便の候補)。
- `affine_warp` / `affine_trans_image`(geometry): 下記のとおり画素一致 5e-3 が原理的に満たせず対象外。
- `cv_*` / `sk_*` / `xsk_*`: 本体が OpenCV / scikit-image(CPU ライブラリ)の包みなので対象外。
- `clahe`(gray): タイル分割 + 双線形ブレンドの逐語再現が大きく、この便では着手しなかった。


幾何ワープ系(`affine_trans_image` など)は ndimage の 3 次スプライン補間 vs grid_sample 双線形で画素一致 5e-3 を満たせない(既存 `projective_trans_region` と同じ理由)ため、この便では候補から外した(採否は IoU/count 指標が要る別枠)。
