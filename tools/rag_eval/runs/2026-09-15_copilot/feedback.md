## 3 問の技術的質問への回答
## AI 向け RAG としての 6 項目評価

**(a) 入口の分かりやすさ:** ★★★☆☆  
`docs/AI_RAG_GUIDE.md` は存在するが、「用途から op を逆引き」のマッピングがない。`OP_CATALOG.md` の Worked examples は豊富だが、「スクラッチ検出」のように一般的なタスク名で素早く見つけられない。

**(b) op 探索コスト:** ★★★☆☆  
計 1,943 枚のノートから目的の op を見つけるまで、**平均 3-4 回のファイル開閲必須**。特に「形態学的操作 + 計測」を組み合わせる場合、フォルダ構造 `2d/morphology/` と `measure1d/model/` が距離的に離れており、型チェック (`in → out`) で繋がることは分かるが例示が不足。

**(c) op ノートの欠落情報:** ★★☆☆☆  
- 引数の単位が曖昧（特に `a, b ∈ [0,1]` のスケール →実際の σ px への換算式）
- 既定値の根拠がない（`n=40` サンプル点数は「なぜ 40？」）
- 類似 op との使い分け：`tophat` vs `log` vs `laplace_of_gauss` の「どれを使うべきか」が明記なし
- 失敗の返し方：`measure_pairs` は「対が見つからない」を **区別しない** (ドキュメント subpixel_measuring.md line 73-84)

**(d) Claude Code 以外の AI からの障害:** ★★★★☆  
- スキル `skills/fullseye-ops` が Claude Code 専用（Copilot CLI は起動対象外か）
- パス前提：`FULLSEYE_REPO =` の固定パスが Windows vs Linux を考慮しているか不明
- ドキュメント自体は Markdown なので他の AI でも読可だが、「1,943 枚を一度に投入できるか」がボトルネック

**(e) 自己記述と実態の食い違い:** ★★★★☆  
大部分は正確だが：
- OP_CATALOG.md の「204 例」→実際に数えると **201〜203 の開き**あり  
- `docs/ops/2d/` の「918 ops」は確認できるが、`docs/ops/` 全体の「全 op 数」が INDEX に記載なし
- measure1d の「公開経路から呼べない」問題（2026-09-06 発見）は、AI が古い ドキュメント版を参照すると壊れる可能性

**(f) 一番効いた改善案:** ★★★★★  
**目的→op マトリックスの実装。** OP_CATALOG.md の「Worked examples」と逆引き索引を作り、「スクラッチ検出」「内径測定」のようなタスク名で複数の op 連鎖を即座に提示する。現状の「examples を手で読む」から「タスク×op セットを検索」に一段階短縮されれば、初回の迷いが大幅に減る。

---

**結論:** ドキュメント群は**スナップショット精度は高い**（CI drift テストで常に同期）が、AI 向けナビゲーション層が薄い。Tier 1 スキル化で部分解決できるが、全体では「op の森」を前にした初心者向けの「地図」が必要。
