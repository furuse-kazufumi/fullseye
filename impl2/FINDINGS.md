# 第 2 実装との突き合わせで出たもの(第 1 次、2026-09-16)

`tools/impl2/pilot.py` —— **op ノートだけ**をローカル LLM(`qwen2.5-coder:32b`)に渡して
C の第 2 実装を書かせ、構造つきの探針で Fullseye と突き合わせた結果。参照実装もテストも
期待値も渡していない(同じソースから機械翻訳した C は解釈ごと複製されるので第 2 実装に
ならない)。

## 走らせた 7 op と判定

| op | 種別 | worst diff | 判定 |
|---|---|---|---|
| `bit_not` | 点処理 | **0.000e+00** | 一致(**陰性対照** —— 近傍を使わない op で一致したので、ハーネス自体は健全) |
| `gdilate` | 近傍 | **0.000e+00** | 一致 |
| `mean_box` | 近傍 | 1.944e-01 | **仕様の穴: 端の規約** |
| `cv_box` | 近傍 | 1.956e-01 | **仕様の穴: 端の規約** |
| `cv_erode` | 近傍 | 1.000e+00 | **仕様の穴: 端の規約**(内部は完全一致) |
| `cv_scharr` | 近傍 | 2.500e+01 | **仕様の穴: 正規化の定義** |
| `gamma` | 点処理 | 6.020e-01 | **第 2 実装の欠陥**(+ 補間則が未記載) |

食い違い 5 件のうち **4 件が仕様(ノート)の穴**、1 件が第 2 実装側の欠陥。

## 一致した 2 件をどう読むか

**一致は成果ではなく警告でもある。** 差分検査が何も見つけないときは、実装が正しいのでなく
**探針が弱い**ことをまず疑う([[feedback_one_probe_input_is_not_coverage]])。`bit_not` は
点処理なので一致して当然(むしろ一致しなければハーネスが壊れている = 陰性対照として置いた)。
`gdilate` の一致は探針を増やして再確認する余地がある。

## 判定の第一問は「どちらが正しいか」ではない

**「契約が決めているか」を先に問う。** 決めていなければ直すのは実装ではなく仕様のほう
([[feedback_second_implementation_finds_what_tests_cannot]] の How to apply #1)。

### 例: `mean_box`(最初に見つけた 1 件の全経緯)

- 角の衝撃に対し **Fullseye は 4/9**(角画素を 4 回数えて `k^2` で割る = reflect 系)、
  **第 2 実装は 1/4**(範囲内の 4 画素だけ数えて 4 で割る)。
- 中心衝撃で残った 0.0033 も端で説明できた: 端に近い出力画素の `1/64 - 1/81 = 0.003279`。
- **窓サイズの対応(`a` -> 3/5/7/9)は両者完全に一致**。つまり食い違いは端だけ。
- ノートは窓サイズを書いているのに、**端の扱いを一言も書いていない**。そして端の規約は
  答えを **値域の 19.4%** 動かす。

### 例: `gamma`(第 2 実装側の欠陥)

ノートは「`a` が指数 γ を **0.5〜2.0** に振る」と書いている。第 2 実装は `pow(v, a)` と
書き、**明記された範囲を無視**した。Fullseye の実測は **γ = 0.5 + 1.5·a(線形)** で
ノートどおり。ただしノートは**範囲は書くが補間則(線形か幾何か)を書いていない** ——
幾何補間なら a=0.5 で γ=1.0 になり、線形の 1.25 と食い違う。**残る穴は本物**。

## 同じクラスを台帳全体で数えた(掃き出し)

一件直して終わりにしない。**同クラスが兄弟にどれだけ広がっているか**を数えた
([[feedback_same_bug_class_recurs_check_siblings]])。

| 欠落クラス | 母数 | 沈黙 | 率 |
|---|---|---|---|
| **端の規約**(近傍窓を使う op) | 213 | **198** | **93.0%** |
| **正規化の式**(「正規化」と書く op) | 185 | **113** | **61%** |
| **つまみの補間則**(「X〜Y に振る」と書く op) | 55 | **45** | **82%** |

いずれも「答えを大きく動かすのに書かれていない」決定である。外部 AI(Codex / Copilot)が
2026-09-15 の聞き取りで「op ノートに単位・既定値の根拠・決定表が足りない」と独立に
指摘していた件の、**定量的な裏付け**でもある(`docs/RAG_EVAL.md`)。

## 直し方(推測で書かない)

穴を埋めるとき、**規約を推測で書いてはいけない**。`mean_box` でやったように
**実測して**書く —— 角に衝撃を置いて応答を見れば、`4/9` なら reflect 系、`1/4` なら
範囲内のみ、`1/9` なら 0 埋めと判別できる。書いたあとは**規約がノートに在ることを
検査する門**を立てる(書き忘れが再発しないように)。

## 生成物を残す理由

判定に関わらず `impl2/c/<op>.c` と `impl2/meta/<op>.json`(来歴: モデル名・ノートの
sha256・探針ごとの差)を残す。第 2 実装は検証器であると同時に、**Python を載せられない
現場で動く実装**でもある。いま `fs_apply` が Python 無しで動かせるのは契約の 5 op だけで、
残りは埋め込み CPython 経由(Python の無い機械では `FS_E_NO_PYTHON`)。差分が解消した
第 2 実装は native 経路へ昇格できる資産になる —— 捨てるとその道が消える。
