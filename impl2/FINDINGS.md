# 第 2 実装との突き合わせで出たもの(第 1 次、2026-09-16)

`tools/impl2/pilot.py` —— **op ノートだけ**をローカル LLM(`qwen2.5-coder:32b`)に渡して
C の第 2 実装を書かせ、構造つきの探針で Fullseye と突き合わせた結果。参照実装もテストも
期待値も渡していない(同じソースから機械翻訳した C は解釈ごと複製されるので第 2 実装に
ならない)。

## 走らせた 7 op と判定

| op | 種別 | worst diff | 判定 |
|---|---|---|---|
| `bit_not` | 点処理 | **0.000e+00** | 一致(**陰性対照** —— 近傍を使わない op で一致したので、ハーネス自体は健全) |
| `gdilate` | 近傍 | **0.000e+00** | 一致 |
| `mean_box` | 近傍 | 1.944e-01 | **仕様の穴: 端の規約** |
| `cv_box` | 近傍 | 1.956e-01 | **仕様の穴: 端の規約** |
| `cv_erode` | 近傍 | 1.000e+00 | **仕様の穴: 端の規約**(内部は完全一致) |
| `cv_scharr` | 近傍 | 2.500e+01 | **仕様の穴: 正規化の定義** |
| `gamma` | 点処理 | 6.020e-01 | **第 2 実装の欠陥**(+ 補間則が未記載) |

食い違い 5 件のうち **4 件が仕様(ノート)の穴**、1 件が第 2 実装側の欠陥。

## 一致した 2 件をどう読むか

**一致は成果ではなく警告でもある。** 差分検査が何も見つけないときは、実装が正しいのでなく
**探針が弱い**ことをまず疑う([[feedback_one_probe_input_is_not_coverage]])。`bit_not` は
点処理なので一致して当然(むしろ一致しなければハーネスが壊れている = 陰性対照として置いた)。
`gdilate` の一致は探針を増やして再確認する余地がある。

## 判定の第一問は「どちらが正しいか」ではない

**「契約が決めているか」を先に問う。** 決めていなければ直すのは実装ではなく仕様のほう
([[feedback_second_implementation_finds_what_tests_cannot]] の How to apply #1)。

### 例: `mean_box`(最初に見つけた 1 件の全経緯)

- 角の衝撃に対し **Fullseye は 4/9**(角画素を 4 回数えて `k^2` で割る)、
  **第 2 実装は 1/4**(範囲内の 4 画素だけ数えて 4 で割る)。
- 中心衝撃で残った 0.0033 も端で説明できた: 端に近い出力画素の `1/64 - 1/81 = 0.003279`。
- **窓サイズの対応(`a` -> 3/5/7/9)は両者完全に一致**。つまり食い違いは端だけ。
- ノートは窓サイズを書いているのに、**端の扱いを一言も書いていない**。そして端の規約は
  答えを **値域の 19.4%** 動かす。

### 例: `gamma`(第 2 実装側の欠陥)

ノートは「`a` が指数 γ を **0.5〜2.0** に振る」と書いている。第 2 実装は `pow(v, a)` と
書き、**明記された範囲を無視**した。Fullseye の実測は **γ = 0.5 + 1.5·a(線形)** で
ノートどおり。ただしノートは**範囲は書くが補間則(線形か幾何か)を書いていない** ——
幾何補間なら a=0.5 で γ=1.0 になり、線形の 1.25 と食い違う。**残る穴は本物**。

## 同じクラスを台帳全体で数えた(掃き出し)

一件直して終わりにしない。**同クラスが兄弟にどれだけ広がっているか**を数えた
([[feedback_same_bug_class_recurs_check_siblings]])。

| 欠落クラス | 母数 | 沈黙 | 率 |
|---|---|---|---|
| **端の規約**(近傍窓を使う op) | 213 | **198** | **93.0%** |
| **正規化の式**(「正規化」と書く op) | 185 | **113** | **61%** |
| **つまみの補間則**(「X〜Y に振る」と書く op) | 55 | **45** | **82%** |

いずれも「答えを大きく動かすのに書かれていない」決定である。外部 AI(Codex / Copilot)が
2026-09-15 の聞き取りで「op ノートに単位・既定値の根拠・決定表が足りない」と独立に
指摘していた件の、**定量的な裏付け**でもある(`docs/RAG_EVAL.md`)。

## 直し方(推測で書かない)

穴を埋めるとき、**規約を推測で書いてはいけない**。`mean_box` でやったように
**実測して**書く —— 角に衝撃を置いて応答を見れば、`4/9` なら reflect 系、`1/4` なら
範囲内のみ、`1/9` なら 0 埋めと判別できる。書いたあとは**規約がノートに在ることを
検査する門**を立てる(書き忘れが再発しないように)。

## 生成物を残す理由

判定に関わらず `impl2/c/<op>.c` と `impl2/meta/<op>.json`(来歴: モデル名・ノートの
sha256・探針ごとの差)を残す。第 2 実装は検証器であると同時に、**Python を載せられない
現場で動く実装**でもある。いま `fs_apply` が Python 無しで動かせるのは契約の 5 op だけで、
残りは埋め込み CPython 経由(Python の無い機械では `FS_E_NO_PYTHON`)。差分が解消した
第 2 実装は native 経路へ昇格できる資産になる —— 捨てるとその道が消える。

# 第 2 次(同日): 別モデルを当て、規約を実測で確定した

## 訂正: 「角で 4/9 だから reflect 系」は**確定していなかった**

上で `mean_box` の角の応答 4/9 から「reflect 系」と書いたが、**その探針では
`reflect` と `edge`(端画素の複製)を区別できない** —— k=3 の角ではどちらも 4/9 に
なる。実際そうなった: ローカル LLM は「範囲内だけ数える」(角 1/4)、**Codex は
「最近傍の端画素を複製」**(角 4/9)を選び、**角の値だけは Fullseye と一致**したのに
全体の最悪差は 0.407 と、ローカル LLM の 0.194 より大きかった。
**一致したときは探針を疑う**([[feedback_one_probe_input_is_not_coverage]])が、
自分の結論にそのまま当たった。

## 別モデルを当てる意味(N-version の相関故障)

同じ op ノートを 2 つのモデルに渡したら、**沈黙点で別の選択**をした:

| 書き手 | 端の選択 | 角 out[0,0] | 全体の最悪差 |
|---|---|---|---|
| Fullseye(正) | (下で実測) | 0.444444 | — |
| `qwen2.5-coder:32b` | 範囲内の画素だけ数えて割る | 0.25 | 0.194 |
| `codex` | 最近傍の端画素を複製 | 0.444444 | 0.407 |

**書き手を変えることが、解釈の相関を下げる唯一の直接的な手段**である。1 モデルで
何本書かせても解釈は相関する。成果物はモデルごとに `impl2/c/<engine>/<op>.c` に残す。

## 規約をカーネル非依存に実測する(`tools/impl2/border_probe.py`)

op が内部で規約 P で埋めているなら、**あらかじめ P で埋めた画像に op をかけて内側を
切り出したもの**は、埋めずにかけたものと一致する::

    op(pad_P(img))[crop] == op(img)   <=>   op の内部規約が P

窓の形も大きさも知らずに判定でき、**どれも一致しなければ「判定不能」と正直に返す**
(勝手に一番近いものを選ばない)。点処理(`bit_not` / `gamma`)は候補が全部一致するので
`ambiguous` と出る —— 端が効かない op では規約が定義されない、という正しい答え。

## 実測結果: 同じ族の中で規約が 5 通りに割れている

`smoothing` の 48 op を測った:

| 規約 | 本数 |
|---|---|
| `symmetric`(端画素を重複させて折り返す = scipy 既定の `reflect`) | 13 |
| `reflect`(端画素を重複させない = OpenCV の `BORDER_REFLECT_101`) | 7 |
| **`wrap`(反対側へ巻き付ける = 周期)** | 3 |
| `edge`(端画素を複製) | 2 |
| `constant0`(外側 0) | 1 |
| 判定不能(大域正規化などで前提が成り立たない) | 22 |

**`mean_box` は `symmetric`、`cv_box` は `reflect`。同じ「矩形平均」なのに端が違う。**
真相は「scipy 系の op は scipy 既定、OpenCV 系の op は cv2 既定」で、**どちらもノートに
書かれていない**。利用者から見れば、名前も説明もほぼ同じ 2 つの op が端で違う答えを
返す。`gauss` の reflect 半画素ずれ(0.1.11 で直した)と**同型の再発**である
([[feedback_same_bug_class_recurs_check_siblings]])。

`wrap` が 3 本あるのは特に意外で、周期境界は画像処理では非自明な選択。書かれていなければ
利用者も第 2 実装も当てられない。

## 直した分(2026-09-16)

測って確定したものを **`ops.py` の docstring** に書き戻した(ノートは生成物なので、
直すのは生成元)。`opdocs md` で 1,947 枚を再生成し、該当 3 枚が更新された。
関連する門 172 件は緑。

**まだ残っている**: `smoothing` の determined 25 本のうち、コア registry から関数を
引けたのは 4 本だけ。`xcv_` / `xkor_` / `xsp_` / `xwt_` / `xpil_` 等の拡張 op は別の
モジュールで登録されており、対応表をたどる作業が要る。他の category(morphology /
rank / edges / texture / frequency / restoration)も未測。

# 第 4 次(同日): region 層へ網を広げた —— 連結性の沈黙

region は **同形の float64 で値が {0,1} のマスク**として返る。つまり既存の C 契約
(double 入出力・同形)がそのまま使え、`image->region`(83)と `region->region`(87)に
網を張れる。**離散の決定(連結性・境界の開閉・空集合)が答えを変える層**で、
`connection` の 4/8 食い違い(0.1.11 で直した実物)が出たのもここ。

探針も二値構造に替えた。要は **斜めだけで触れる 2 つの塊** —— 4 連結なら 2 個、
8 連結なら 1 個になる。市松・穴あき・角で接する矩形・端で切れる塊・空集合・単画素も入れた。
**乱数では絶対に出ない**。

## region->region の第 1 便(6 op)

| op | 判定 | 食い違った探針 |
|---|---|---|
| `fill_holes` | **仕様の穴: 連結性** | `checkerboard8` と `ring_with_hole` **だけ**。穴の判定に使う背景の連結性(4/8)が未定義 |
| `boundary` | **仕様の穴: 端** | `all_ones` と `blob_at_corner` **だけ**。領域が画像の端に接するとき、画像の縁を境界とみなすかが未定義 |
| `fill_up` | 第 2 実装の疑い | `all_zeros` でも食い違う = 意味の取り違え |
| `dilation_circle` | 一致 | — |
| `convex_fill` / `em_skeleton` | コンパイル失敗 | 第 2 実装側 |

**食い違う探針が 2 つだけ**というのが効いている —— どこが沈黙点かを名指しできる。
`fill_holes` は `connection` の 4/8 と**同じクラスの兄弟**で、直したはずの欠陥クラスが
別の op に残っていた形([[feedback_same_bug_class_recurs_check_siblings]])。

## 連結性の沈黙を台帳全体で数えた

| | 母数 | 沈黙 | 率 |
|---|---|---|---|
| **連結性**(region を食う/返す op) | 215 | **168** | **78.1%** |

これで欠落クラスは 4 つ: **端の規約 93%** / **正規化の式 61%** / **つまみの補間則 82%** /
**連結性 78%**。

## 連結性は「一発で確定する汎用手法」が無い —— だから差分に見つけさせる

端の規約は `op(pad_P(x))[crop] == op(x)` という**カーネル非依存の恒等式**で機械的に
確定できた。連結性にはこれに当たるものが無い(op ごとに意味が要る)。
**無いものを在るふりをしない**。代わりに第 2 実装との差分に見つけさせる ——
`fill_holes` は実際それで出た。探針が「どこで分かれるか」を名指しするので、
triage は 1 op ずつでも回せる。

# 第 5 次(同日): つまみを実測 —— そして**バグを 1 件でっち上げる寸前だった**

## 先に、やりかけた誤り

`tools/impl2/knob_probe.py` の最初の版は **探針 1 枚**(縞模様の合成画像)で測っていた。
それで `xcv_stylization` の ``a`` が「まったく効かない」と出た。実装を見ると

    cv2.stylization(_to3(v), sigma_s=20 + 100*a, sigma_r=0.1 + 0.4*b)

とつまみは**確かに配線されている**。「配線はあるのに死んでいるつまみ」= 本物のバグ、
と報告しかけた。

止まって切り分けた。`cv2.stylization` を**直接**同じ画像で叩いても差は 0。では cv2 の
問題かというと、**入力をテクスチャ + 雑音に替えると同じ 24x24 で ``sigma_r`` が出力を
184/255 動かした**。つまり **op は正常で、探針がパラメータを励起できていなかっただけ**。

[[feedback_one_probe_input_is_not_coverage]] —— 「門が正しい場所でも探針 1 枚だと
どのノブでも死ぬ op を見逃す」。今回はその裏返しで、**探針 1 枚が生きているノブを
死んでいると誤診した**。

## 探針を 4 枚にして測り直した(傾斜+縞 / テクスチャ+雑音 / 塊と穴 / 最高周波)

| 項目 | 探針 1 枚 | **探針 4 枚(正)** |
|---|---|---|
| ``b`` を実際に使う op | (標本 6 本で 1) | **114 / 378** |
| 「``b`` は未使用」の誤記 | 0 | **0**(強い探針でも 0 = 検証済み) |
| **1 枚なら誤判定しえた op** | — | **80 本(21%)** |

**80 本**は「ある探針では効果ちょうど 0、別の探針では大きく動く」op だった。1 枚で
測っていたら最大 80 件の偽「未使用」を作り、そのうち何件かを「バグ」として報告して
いた。**発見ゼロが未実行のサインであるのと同じくらい、発見アリが探針の弱さのサイン
でもある。**

## 測って分かったこと

| ``a`` の効き方 | 本数 |
|---|---|
| 連続 | 180 |
| 段階(離散) | 99 |
| 効かない | 99 |

- **``a`` が実測で効かないのに、ノートがそう書いていない op が 12 本**。利用者は
  効かないつまみを回して調整しようとする。
- **段階的なのに切り替え位置が書かれていない op が 18 本**。「3,5,7,9 に振る」とだけ
  書いてあって a=0.5 が 5 なのか 7 なのか分からない。実測では `mean_box` が
  a ≈ 0.25/0.49/0.75、`cv_box` が a ≈ 0.33/0.67/0.99 で **同じ「4 段階」でも切り替わる
  位置が違う**。

`docs/op_knob.json` に実測を置き、ノート生成器が**黙っている op にだけ**差し込む。
56 枚が更新された。門 176 件は緑。

# 第 6 次(同日): **89 op が「画像間で比較できない値」を返していて、1 本も書いていなかった**

`cv_scharr` の第 2 実装が出力スケールごと食い違った(最大 25.0)。ノートは
「正規化したもの」とだけ書いて**式が無い**。実測すると ``|Sx| + |Sy|`` を
**その画像の最大値**で割っていた(`raw/max` と完全一致 0.000e+00。定数画像でも
0 除算にならず 0 を返す)。

**これは測る道具にとって致命的になりうる性質**である。画像ごとに割ると:

* **同じ強さの特徴でも、その画像で最も強い特徴が何かによって値が変わる**
* **弱い特徴しか無い画像では雑音が 1.0 まで持ち上がる**
* 明るさだけ変えた同じ被写体は同じ値を返す(スケール不変)

つまり **値を画像間で比較できない**。検査のしきい値を 1 枚で決めて別のロットに適用する、
という一番ありふれた使い方が壊れる。

## 機械的に洗った(`tools/impl2/norm_probe.py`)

**2 つの署名が同時に揃うこと**で見分ける —— (1) 出力の最大が複数の入力で常にちょうど
1.0、(2) 入力を定数倍しても出力が 1 ビットも変わらない。片方だけなら別の説明が付く
(最大が 1.0 だけ = 飽和、スケール不変だけ = 二値化)。**確信が持てない形は報告しない。**

| | 件数 |
|---|---|
| image->image で画像ごとに正規化している op | **89** |
| そのうちノートがそう書いているもの | **0** |
| **沈黙率** | **100%** |

`bothat` `corner_response` `cv_corner_harris` `cv_laplacian` `cv_scharr` `dog`
`derivate_gauss` `frei_amp` `gray_range_rect` … エッジ・コーナー・勾配・形態学の
差分系がまとめて該当する。**どれも「強さ」を返す op** で、利用者が最もしきい値を
決めたくなる種類のものばかりである。

89 枚のノートに注意書きを入れ、**消えないように門を立てた**(署名の片方だけで
「画像ごと」と断じていないことも同時に検査する)。

## これで見つかった欠落クラスは 5 つ

| クラス | 母数 | 沈黙 | 率 |
|---|---|---|---|
| 端の規約 | 213 | 198 | 93% |

### 測ったもの: `tools/impl2/blank_probe.py`

**一様な画像を入れて、明るさ c を 0.00〜1.00 まで掃く。** 端の規約には
`op(pad_P(x))[crop] == op(x)` という恒等式があり、連結性にはそれが無くて確定手段を
作れなかったが、ここは恒等式すら要らない —— **推測する余地が無い**。

報告するのは (1) 定数画像に定数を返すか (2) c を上げると出力が跳ぶか (3) c に依らず
常に同じ値か、の 3 つだけ。**跳びが穴かどうかは判定しない**(固定しきい値の op が
0.5 で跳ぶのは正しい動作)。陽性対照つき(跳び/一定/なめらかの 3 参照)。

全 image op 378 本を掃いて **364 本を測定、27 本が跳んだ**。

### 見つけた不具合

**(1) 適応的しきい値が平坦面で全面誤検出になる —— 3 op / 4 か所**

`v > filter(v) + offset` は既定(`b=0.5` でオフセット 0)では「**1 ULP でも明るければ
前景**」を意味する。一様な面でも `uniform_filter` の積算順序で結果が最下位 1 ビット
下に丸まることがあり、そのとき面の全画素が前景になる:

| 明るさ | 前景 / 576 | `uniform_filter(v) - v` |
|---|---|---|
| 0.04 | 0 | 0.0 |
| **0.05** | **576** | **-6.939e-18** (= `spacing(0.05)` ちょうど) |
| 0.06 | 0 | 0.0 |

`dyn_threshold` / `adaptive_gauss_thresh` / `local_threshold`。
**同じ式が `ops.py` と `backends_auto.py` に別実装として重複**しており、
`ops.py` だけ直したら `fs.apply` はもう片方を呼んでいて直らなかった
([[feedback_second_implementation_finds_what_tests_cannot]] の「同じ op の backend が
分岐していた」と同じ型)。`_FLAT_TOL = 1e-9` を両方に置いた —— 16-bit の量子化幅
(1.5e-5)より 4 桁小さく実信号を削らず、丸め屑(1e-17)より 8 桁大きい。

**(2) 局所分散が一様面で最大値を返す —— 3 op**

`E[x²] − E[x]²` の桁落ちで一様画像にも 1e-15 級の偽分散が残り、**`sqrt` がそれを
3e-8 へ 8 桁持ち上げて** `_norm` の床(1e-8)を越え、正規化で全画素 1.0 になる。
空フレームが「全面が最大テクスチャ」として返る(一様 0.51 で全画素 1.0、0.50 で 0.0)。

**この不具合は GPU 経路 `accel.py:_std_filter` では既に診断されて直っていた** ——
コメントに「平坦画像でも偽分散が残る」「`sqrt` が増幅し `_norm_b` の素通し閾値を
超えてフルスケール化する」と書いてある。**CPU 経路、つまり既定のほうだけが直って
いなかった**。torch を入れていない利用者全員が壊れたほうを踏む。

CPU 側は閾値ではなく**平均を引いてから分散を取る**形に替えた(一様画像で厳密に 0 に
なるので素性が良い)。`std_filter` / `deviation_image` / `texture_laws`。

**(3) kornia 経路の正規化の床が丸め屑より下 —— 2 op**

kornia は float32 で計算するので、一様画像にゼロ和カーネル(ラプラシアン・DoG)を
当てても 1e-7 級の屑が残る。`_norm` の床が `1e-8` = **屑より下**にあったため、
屑が床を跨ぐたびに出力が 0 と全面 1.0 の間で反転していた
(一様 0.09 で全画素 1.0、0.08 で 3.6e-9)。

床を**入力の大きさに対する相対量** (`1e-5 × |入力|max`) に直した。固定値にすると
最大 1e-3 のような暗い画像で本物の弱い応答まで消える —— 1000 倍暗い画像でも応答が
残ることを確認済み。`xkor_laplacian` / `xkor_dog`。

**(4) 方向マップの同点を丸め屑が破っていた —— 3 op**

一様面ではコンパス応答も Frei-Chen 応答も数学的に厳密に 0 になるが、浮動小数では
2e-15 級の屑が残る。`argmax` / `arctan2` は**その屑の大小で勝者を決める**ので、
明るさを 0.49 から 0.51 に変えただけで方向マップが別物になった
(`kirsch_dir`: 0.4286 → 0 → 0.2857)。

方向の意味は変えず、**同点を決定的にする**ために屑を 0 に落とした —— `argmax` は
全 0 なら 0、`arctan2(0,0)` は 0 を返すので、どちらも「勾配なし」の既定値に落ち着く。
`kirsch_dir` / `robinson_dir` / `frei_dir`。実エッジの方向は保たれている
(縦の段差 0.5 / 横の段差 0.75)。

### なぜ既存のテストが素通ししたか

どれも「**たまに出る**」形の壊れ方である。明るさ 0.50 では正しく、0.51 で全面誤検出
になる —— 現場では**再現しない誤報**として現れ、原因に辿り着けない。平均や相関を見る
既存テストは一様入力を使わないので通ってしまう。

門 `tests/test_blank_frame_is_stable.py`(18 件)を足した。一様入力を 0.01 刻みで
101 段掃き、(a) 屑以上を返さないこと (b) **屑を消したせいで信号まで消えていないこと**
(陰性対照 —— `return zeros` で満たせる門を防ぐ) (c) 隣り合う明るさで反転しないこと、
を検査する。さらに **旧の式をその場で再現して、この門が実際にそれを落とすこと**も
検査に入れてある(「新しいコードで緑」は門が何かを守っている証拠にならない)。

### つまみの対応が書かれていない件(6 番目の穴のクラス)

`gamma` が第 2 実装と**全探針で**食い違ったのを追ったら、点処理なのに範囲しか書かれて
いなかった。実測すると厳密に線形:

| `a` | 0.0 | 0.25 | 0.5 | 0.75 | 1.0 |
|---|---|---|---|---|---|
| γ | 0.500000 | 0.875000 | **1.250000** | 1.625000 | 2.000000 |

γ = 0.5 + 1.5a(残差 3e-15)。**既定の `a=0.5` は γ=1.25 であって素通しではない** ——
範囲の真ん中を「何もしない設定」と読むのが自然なので、黙っていると誤用される。
素通しは `a=1/3`(実測: 恒等との差 0.0)。

書き方の正解は既に repo 内にあった —— `gaussian` は「`σ = 0.3 + 2.7a` に**線形に**
振る」と式まで書いている。`gamma` だけが取りこぼされていた。同じ取りこぼしは
**連続つまみ 180 本のうち 166 本(92%)**にある(「振る」と書くのに線形か幾何かを
書いていない)。`gamma` / `gamma_image` / `pow_image` を直した。

**この穴のクラスは機械的には閉じられない。** 内部パラメータを出力から回復できる op
(べき乗族は `log(out)/log(in)` で厳密に回復でき、べき乗でない op では残差が発散して
自動的に「回復不能」と出る)に限られ、一般には測れない —— 連結性と同じ**負の結果**。

### 7 番目の穴のクラス: **精度が黙って 8 bit に落ちる** —— 29 op

codex が `cv_median` で食い違い、差が**厳密に 1/255** だった。追うと Fullseye が内部で
uint8 に量子化していて、ノートには書かれていない。

`tools/impl2/quant_probe.py` を作って全 image op 378 本を測ったら **29 本**が該当し、
そのうち **21 本(72%)が黙っていた**(`cv_clahe` / `cv_nlmeans` / `sk_autolevel` /
`xcv_*` 6 本 / `xpil_*` 9 本 / `xsk3_rank_*` 2 本 ほか)。

**なぜ黙ってはいけないか。** 利用者は float64 の画像を渡すので、渡した精度がそのまま
出てくると思う。実際には 255 段に潰れるので、16-bit カメラの階調(1.5e-5)は
1/255 = 3.9e-3 に丸められて意味を失い、1/255 より小さい差しか無い 2 枚は**同じ答えを
返す**(微小な欠陥が消える)。出力は k/255 の格子にしか乗らないので、微分や回帰に
渡すと段差が出る。Fullseye は「測る道具」を名乗っている以上、これは書かねばならない。

**署名の立て方を一度間違えた。** 最初は「1/255 より小さく揺らしても出力が変わらない」
を第 2 の署名にしたが、**陽性対照が落ちた** —— 量子化する参照実装でも、揺らしが丸め
境界を跨げば出力は 1 段変わる。鈍さは量子化の署名ではない。立て直した署名は
(1) 出力がすべて k/255 の格子に載る (2) その格子を 20 段以上使っている、の 2 つ。
陽性対照には**二値化の囮**を入れてある —— (1) だけを署名にすると二値出力の op が
該当してしまうので、囮が落ちることを確かめている。

生成器に差し込み(`tools/opdocs.py` の `_with_quantisation`、ノートが黙っている場合に
限る)+ 門(`tests/test_op_quantisation_documented.py`)を置いた。
